Here are practical options for running Playwright so tests can actually pass, given Vercel’s read-only serverless environment.

---

### 1. **Dedicated runner service (recommended)**

Run tests on a host that has a writable filesystem and can install/run Playwright. Your Vercel API only orchestrates; it doesn’t run Playwright itself.

- **Railway / Render / Fly.io**  
  Deploy a small Node service that:
  - Exposes an endpoint like `POST /run` (accepts project/plan/case and optional stream flag).
  - Clones or receives test definitions, runs Playwright in that environment, streams or returns results.
  - Writes run results to Firestore (or another store TestGrid already uses).

- **Flow:** TestGrid frontend → Vercel API → your runner service → Firestore. Frontend can keep calling your existing Vercel API; only the serverless function’s implementation changes (it forwards to the runner and/or reads from Firestore).

- **Pros:** Full control, real filesystem, can stream logs.  
- **Cons:** You operate and pay for the runner (often a few dollars/month).

### 2. **CI job (e.g. GitHub Actions)**

Don’t run Playwright on Vercel at all. Trigger a CI workflow that runs Playwright and reports back.

- **Flow:** TestGrid (or Vercel API) triggers a workflow (e.g. GitHub Actions) via repo_dispatch or a “trigger workflow” API. The workflow runs Playwright, then pushes results to Firestore (or a small API) via a token or webhook.

- **Pros:** No extra server to maintain; GitHub gives you a real Linux environment.  
- **Cons:** Need to wire trigger + result storage; runs are async (poll or “run history” page to see results).

Use a service that runs browser/Playwright for you.

- **BrowserStack, Sauce Labs, LambdaTest, etc.**  
  Your backend (or the dedicated runner above) uses their APIs/SDKs to start a session, run the test script, and get results. TestGrid still stores runs in Firestore; the “runner” is their grid.

- **Pros:** No infra for browsers; good for cross-browser.
