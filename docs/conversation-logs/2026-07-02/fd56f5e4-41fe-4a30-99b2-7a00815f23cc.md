## Assistant

On macOS, use one of these to recursively find MP3 files:

## Using `find` (built-in)

```bash
find /path/to/search -name "*.mp3" -type f
```

**Examples:**
- Search from your home directory:
  ```bash
  find ~ -name "*.mp3" -type f
  ```
- Search from current directory:
  ```bash
  find . -name "*.mp3" -type f
  ```
- Search entire system (requires sudo for some directories):
  ```bash
  find / -name "*.mp3" -type f 2>/dev/null
  ```
  (The `2>/dev/null` suppresses permission denied errors)

## Using `mdfind` (macOS Spotlight)

```bash
mdfind "kMDItemContentType == 'public.mp3'"
```

This uses Spotlight's index, so it's fast but only finds files that Spotlight has indexed.

## Using `fd` (if installed)

If you have `fd` installed (via Homebrew: `brew install fd`):
```bash
fd -e mp3
```

## Quick tip

To search just your projects folder:
```bash
find ~/projects -name "*.mp3" -type f
```

The `find` command is the most reliable since it's built into macOS and doesn't depend on indexing.

**Playwright** is an open-source **browser automation and testing** library from Microsoft. It’s mainly used for **end-to-end (E2E) and integration testing** of web apps, and can also drive browsers for scraping or other automation.

## What it’s for

- **End-to-end testing** – Simulate real users: open pages, click, type, navigate, and assert that the app behaves correctly.
- **Cross-browser testing** – Same tests can run on **Chromium**, **Firefox**, and **WebKit** (Safari).
- **Reliable automation** – Built-in waiting and retries, so tests are less flaky than with raw Selenium.
- **CI/CD** – Run tests in GitHub Actions, Jenkins, etc., including in headless mode.

## What it can do

| Area | Capabilities |
|------|----------------|
| **Browsers** | Launch and control Chromium, Firefox, WebKit; mobile viewports; multiple contexts/tabs. |
| **Interactions** | Click, type, select, drag, hover, file uploads, keyboard shortcuts. |
| **Assertions** | Check text, visibility, attributes, URLs, network requests. |
| **Network** | Mock APIs, block requests, capture requests/responses, set headers. |
| **Auth / state** | Log in once, save storage/cookies, reuse in many tests. |
| **Screenshots / video** | Capture screenshots and record video of test runs. |
| **Debugging** | Trace viewer, step-through debugging, watch mode. |

## Typical use

- **E2E tests**: “User can log in, add item to cart, and checkout.”
- **Visual/regression**: Screenshot pages and compare over time.
- **Smoke tests**: “Critical flows load and don’t error.”
- **Scraping / automation**: Scripts that need a real browser (e.g. JS-heavy sites).

In your projects (e.g. **testgrid**, **lil-magnet-memories**) it’s used for **E2E tests**: running the app in a real browser and asserting that key flows work.

You want to test the full journey (cart → checkout → confirmation) without real charges. Here’s a practical way to do it with Playwright.

## 1. **Use redemption / test codes (recommended)**

Using a **test redemption or promo code** that makes the order free (or a fixed $0.01) is a very common and good approach:

- **Pros:** You exercise the real UI and backend flow (coupon validation, order creation, confirmation, emails).
- **Implementation:** In staging/test, create a code like `PLAYWRIGHT_TEST` or `E2E_FREE` that applies 100% off (or fixed $0). Your Playwright test applies it at checkout and completes the flow.
- **Safety:** Only enable that code in non-production (e.g. by environment or a “test codes” list). In production, either don’t create it or disable it.

So yes: **setting up redemption/promo codes to get through the payment step is a solid approach** and works well with Playwright.

## 2. **Use payment provider test mode**

If you use Stripe, PayPal, etc.:

- Use **test API keys** in your test/staging environment.
- Use the provider’s **test card numbers** (e.g. Stripe’s `4242 4242 4242 4242`) in Playwright so the test fills the real payment form.
- No real money moves; you still test the real payment UI and success/failure paths.

You can combine this with a test code (e.g. 100% off so the test never actually charges even the test card).

## 3. **Recommended combo for “buy something” flows**

A practical setup:

1. **Staging/test environment** with test payment keys and test inventory.
2. **Test promo/redemption code** (e.g. `E2E_FREE`) that makes the order $0 so the test can complete checkout without entering card details (or use a test card if you want to test the card form).
3. **Playwright test** that:
   - Adds a product to cart,
   - Goes to checkout,
   - Applies the test code,
   - Either submits with a test card (if you want to test payment UI) or continues with $0 total,
   - Asserts on order confirmation / thank-you page / order ID.

That way Playwright is testing the real “buy something” path without real money, and redemption codes are a clean way to get through the payment step in tests.
